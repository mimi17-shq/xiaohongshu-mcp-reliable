# 产品案例：让 AI Agent 的小红书写操作更可靠

## 一句话介绍

这是一个基于开源项目 [`xpzouying/xiaohongshu-mcp`](https://github.com/xpzouying/xiaohongshu-mcp) v2.5.5 的可靠性改造分支。原项目已经提供登录、浏览、搜索、发布和互动等能力；本项目新增的重点，是降低 AI Agent 在超时、重启和重复调用时造成重复发布、重复评论或回复错楼的风险。

## 问题背景

浏览器自动化的“超时”不等于操作没有发生。一次实际使用中，图文发布在客户端等待约 60 秒后超时，但后台流程继续运行，页面随后确认内容已经发布。如果 Agent 将超时直接当作失败并重新提交，就可能产生重复笔记。

评论回复还有目标歧义：同一用户可能在一篇笔记下留下多条评论，只按用户身份定位，可能回复到错误楼层。多个浏览器页面并发操作同一账号时，也会争抢登录状态和运行资源。

因此，这个项目要解决的不是“让 Agent 调用更多工具”，而是让每次有副作用的操作都可追踪、可核实，并在证据不足时停止盲目重试。

## 需求与成功标准

- 提交发布、顶层评论或评论回复后立即返回任务 ID，Agent 不必一直等待浏览器。
- 相同幂等键和相同参数返回原任务，不再次执行；同一幂等键对应不同内容时拒绝调用。
- 服务重启后恢复尚未执行的任务；已经开始但结果无法证明的任务标记为 `unknown` 或 `uncertain`。
- 回复必须使用精确的 `comment_id`，不能用 `user_id` 猜测目标。
- 无法确认操作结果时，提示 Agent 先检查页面，而不是自动重试。
- 所有浏览器型操作串行执行，避免同一账号被多个页面同时驱动。

## 方案设计

核心流程是：**提交请求 → 持久化任务 → 返回任务 ID → 串行执行 → 记录证据 → 查询终态**。

项目为图文发布、顶层评论和评论回复分别提供状态查询工具。调用方可以传入稳定的 `idempotency_key`；未传入时，系统会对完整请求做 10 分钟摘要去重。回复任务还增加了 `feed_id + comment_id` 目标冷却，即使 Agent 修改正文或更换幂等键，也不能绕过同一目标的重复保护。

结果不再只有“成功/失败”两种：

- `confirmed` / `succeeded`：已有成功证据，不再重试。
- `blocked` / `rejected`：能够确认没有成功，可根据原因处理。
- `unknown` / `uncertain`：可能已经发生，必须先用只读工具或人工核实。
- `wrong_target`：观察到结果出现在错误楼层，停止自动处理。

评论回复会依次记录目标定位、输入、提交、网络请求和页面结果。提交前无法确认目标时会安全中止；提交后发生异常时则保守标记为不确定。

此外，列表、搜索和主页结果只保留 Agent 决策所需字段，并限制返回数量，减少无关图片地址和重复数据对模型上下文的占用。Cookie 删除能力不对 MCP 和 HTTP 路由开放，避免 Agent 误清登录状态。

## 关键决策与取舍

- 选择异步任务，而不是不断延长等待时间：解决客户端断开后的任务追踪问题。
- 正式表达“不确定”：多一次核实步骤，换取更低的重复副作用风险。
- 回复只认评论 ID：牺牲缺少 ID 时的便利性，换取目标唯一性。
- 浏览器全局串行：降低吞吐量，但更符合单账号自动化的资源约束。
- 保留上游署名与许可证：原项目的完整功能不作为个人原创成果，本项目只声明可靠性改造。

## 验证与迭代

仓库测试覆盖任务持久化、幂等冲突、重启恢复、浏览器串行、精确回复、请求目标校验和精简响应。公开发布前已通过 `go test ./...`、`go test -race ./...` 和 `go vet ./...`。

一次真实回复验收中，任务先立即返回 `queued`，约 33 秒后变为 `confirmed`；使用完全相同的幂等键再次调用时返回原任务，页面只出现一条回复。

当前局限是页面自动化仍依赖小红书 DOM 和接口行为，站点更新后可能失效；视频发布仍沿用上游同步流程；当前也没有外部用户规模、长期成功率或重复率数据。自动化存在账号受限或封禁风险，应先使用测试账号验证。
