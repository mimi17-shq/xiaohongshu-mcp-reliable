# 产品复盘：让 AI Agent 的小红书写操作更可靠

## 项目边界

本项目基于开源项目 [`xpzouying/xiaohongshu-mcp`](https://github.com/xpzouying/xiaohongshu-mcp) v2.5.5。登录、浏览、搜索、发布和互动等基础能力来自上游；我提出并验证的是面向 AI Agent 的可靠性改造，不把上游功能作为个人原创成果。

## 问题是怎样出现的

一次真实图文发布中，客户端等待约 60 秒后超时，但后台浏览器仍继续执行，页面随后确认内容已经发布。对 Agent 来说，这种“没有及时拿到成功结果”很容易被理解成“没有发布”，再次调用就可能产生重复笔记。

同一阶段还出现过两个浏览器操作争抢同一账号状态和系统资源。评论回复则有另一类风险：同一用户可以在一篇笔记下留下多条评论，只按用户身份寻找目标，即使回复了正确的人，也可能回复到错误楼层。

这让我把问题从“自动化偶尔失败”重新定义为：**Agent 无法判断一个有副作用的动作是否已经发生，也缺少阻止错误重试的产品机制。**

## 我做出的产品判断

我没有把目标定成“尽量让每次调用都成功”，而是优先保证三件事：

1. 同一个业务动作不能因为超时或重复调用执行两次。
2. 无法证明成功或失败时，系统必须明确表达“不确定”。
3. 回复目标必须可验证，便利性不能高于避免错楼。

在这个原则下，我接受了异步任务、幂等键和浏览器串行带来的额外等待，也没有用自动重试去掩盖异常。因为对发布和评论而言，慢一点通常可以补救，重复或错发却可能不可逆。

## 方案如何形成

最终流程是：**请求先持久化 → 立即返回任务 ID → 浏览器串行执行 → 记录阶段与证据 → 调用方查询终态**。

- 调用方提供稳定的 `idempotency_key`；同一键和参数返回原任务，同一键对应不同内容时拒绝执行。
- 未提供键时，对完整请求做 10 分钟摘要去重。
- 服务重启后恢复尚未执行的任务；执行中断且结果无法证明时标记为 `unknown` 或 `uncertain`。
- 回复必须使用精确 `comment_id`，并在页面定位、网络请求和结果观察三个阶段核对目标。
- 同一 `feed_id + comment_id` 有在途或近期不确定任务时，即使修改正文或幂等键也不能再次提交。
- 所有浏览器型操作共享一个槽位，避免并发驱动同一账号。

Codex 将这些规则实现为任务状态机、持久化文件和自动化测试；我负责判断哪些失败可以安全重试、哪些必须停下来核实，以及最终行为是否符合真实使用预期。

## 使用前后的变化

改造前，调用方只能看到一次同步调用成功或报错；超时后既找不到原任务，也不知道能否重试。改造后，Agent 会先拿到任务 ID，再查询 `queued`、`running`、`confirmed`、`rejected` 或 `uncertain` 等状态。

一次真实评论回复验收中，提交后立即返回 `queued`，约 33 秒后变为 `confirmed`。使用完全相同的幂等键再次调用时，系统返回原任务，页面最终只有一条回复。这次结果证明的不是“所有回复都会成功”，而是重复调用不会再次产生副作用。

列表、搜索和主页结果也改为只保留 Agent 后续决策所需字段并限制数量。目标不是让返回内容看起来更丰富，而是减少图片地址和重复字段对模型上下文的占用。

## 验证与仍未解决的问题

公开版本通过了任务持久化、幂等冲突、重启恢复、浏览器串行、精确回复、请求目标校验和精简响应测试；发布前通过 `go test ./...`、`go test -race ./...` 和 `go vet ./...`。

仍需诚实说明：页面自动化依赖小红书 DOM 和接口行为，站点更新后可能失效；视频发布仍沿用上游同步流程；目前没有外部用户规模、长期成功率或重复率数据。自动化本身也存在账号受限或封禁风险。

## 我的职责

- 从真实超时、并发和回复异常中提出需求并重新定义问题。
- 确定“不确定时先核实，不盲目重试”的产品原则。
- 定义幂等、任务状态、目标冷却、精确定位和验收规则。
- 参与真实页面与任务状态验收，并根据异常样本继续调整优先级。
- 代码实现和自动化测试由 AI 完成；我没有独立编写这些代码。
- 公开整理时保留上游署名、Apache-2.0 许可证、NOTICE 和差异说明。
